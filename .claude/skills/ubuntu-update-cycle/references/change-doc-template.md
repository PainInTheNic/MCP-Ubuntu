# Change Management documentation

## Where it lives

Google Drive, via the Drive MCP tools (`search_files`, `create_file`, etc.). Folder:

**The Drive connector available here is read/create only** — no edit, update, delete,
or trash tool. Get a doc right before creating it; if you need to fix one after the
fact, you have to recreate it and ask Nic to trash the old one (or drive the browser

optional — a wrong `-NNN` means a duplicate you can't clean up yourself.

## Find the next sequence number — always, before creating anything

Other automated processes file docs in this folder too, and so does Nic himself. **Do
not assume you are the first thing writing to today's date.** Query by creation time,
not by title:

```
parentId = '1YcAyiuJxiTKkr_uLY6sfTn0WuOPY52o5' and createdTime > 'YYYY-MM-DDT00:00:00-04:00'
```

Take the highest `-NNN` found for today's date and use the next one. If this comes
back empty and you're not confident that's real (Drive's `title contains '2026.08.20'`
style dotted-date search is known to be unreliable and can miss real siblings), widen
the `createdTime` window by a few days to sanity-check the pattern, and lean on
whatever Nic tells you directly if he states a number — he's looking at the actual
folder UI, which is more trustworthy than an API search here.

## Filename convention

```
YYYY.MM.DD-NNN Title In Title Case
```

- Dots in the date, not dashes.
- `NNN` is a 3-digit sequence, reset per day, starting at `001`.
- **No `CHG-` prefix in the filename** — that prefix belongs only inside the document
  body's H1.
- Title is a short, plain-English description of what changed.

## Document structure

Create via `create_file` with `contentMimeType: text/markdown` — Drive auto-converts
it to a Google Doc. Note: Google's markdown importer flattens fenced code blocks into
plain lines with escaped `#`/backslashes, and tables render with a blank header row
above the bold labels. This matches the existing house style in the folder; don't
fight it.

Use this exact skeleton:

```markdown
# CHG-YYYY.MM.DD-NNN: <Title>

**Date:** YYYY-MM-DD
**Category:** Infrastructure (or Infrastructure / Security, Infrastructure / Database, etc.)
**Risk Level:** Low | Low-Medium | Medium (see guidance below)
**Status:** Completed
**Performed By:** Claude Code (AI Agent) via ubuntu-mcp-server
**Approved By:** Nic

## 1️⃣ Description & Background

What was pending and why, in plain terms. Note anything unusual: phasing overrides,
a kept-back package you had to dist-upgrade around, an execution-strategy change
(e.g. full-parallel instead of the default canary-then-parallel) and why.

## 2️⃣ Changes Made

A per-server table: packages, before/after versions, result, reboot required y/n.
List the actual package set and version deltas. Note any service restarts
(`needrestart`'s output tells you exactly what it bounced) and any config files
touched.

## 3️⃣ Commands Executed (CLI-Style)

The actual commands run, generalized slightly (drop nonce/marker noise) so a human
could follow along and re-run them if needed.

## 4️⃣ Verification & Validation

The concrete evidence each host came back healthy: reboot flag cleared, kernel
version, `systemctl is-system-running`, `--failed` output, and the per-host service
check from `references/servers.md` (Plex media mounts, Portal Apache, PostgreSQL
`pg_isready` + table count). Show actual output, not just "verified".

## 5️⃣ Regression Risk & Rollback Plan

Name the real risks for *this specific change* (a glibc bump carries different risk
than a MOTD config package) and how they were mitigated or ruled out. Include an
actual rollback command using the old version numbers — `apt-get install
pkg=<old-version>`, plus `sudo reboot` if glibc/kernel was involved.

---

*Document generated by Claude Code — YYYY-MM-DD HH:MM TZ*
```

Get the timestamp for the footer from an actual server (`date '+%Y-%m-%d %H:%M %Z'`)
rather than guessing — session clocks and server clocks can disagree, and dating
correctly matters for the sequence-number check on any future doc filed the same day.

## Risk level guidance

- **Low:** routine library/tooling patches, no kernel, no reboot, or a reboot that's
  purely a formality (e.g. firmware blobs with no service impact).
- **Low-Medium:** a kernel or glibc update requiring a real reboot on one or more
  hosts, run with the default canary-then-parallel staging.
- **Medium:** the same, but run fully in parallel across all three at once (the
  staged safety margin was intentionally skipped) — say so explicitly in both the
  background section and the risk section, don't just pick "Medium" without
  explaining why.
